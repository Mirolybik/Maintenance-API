# Сервис учёта технического обслуживания оборудования (Maintenance API)

Промышленный REST API сервис для диспетчеризации и учёта технического обслуживания оборудования распределённых ветропарков и энергетических объектов. Сервис защищён аутентификацией с ролевым разграничением доступа (RBAC), развёрнут за обратным прокси-сервером Nginx в изолированной сети Docker и подключён к сквозному мониторингу на базе Prometheus и Grafana.

---

## 1. Архитектура и схема развёртывания

Стек приложения полностью контейнеризирован через Docker Compose и запускается в закрытом сетевом контуре (`bridge`). Прямой доступ к Node.js приложению и базе данных PostgreSQL снаружи заблокирован; публичным является только HTTP-порт Nginx (`:80`). Grafana доступна на хосте только по `127.0.0.1:3001`, Prometheus и миграции работают внутри сети Docker.

```text
               HTTP Запросы (:80)
                       │
                       ▼
          ┌─────────────────────────┐
          │   Nginx Reverse Proxy   │ (Gzip, Proxy headers, X-Request-Id)
          └────────────┬────────────┘
                       │ proxy_pass (внутренняя сеть Docker)
                       ▼
          ┌─────────────────────────┐
          │     Node.js Express     │ (Многоступенчатая сборка, запуск от user: node)
          │    (Maintenance API)    │
          └──────┬───────────┬──────┘
                 │           │
      SQL (Pool) │           │ /metrics (Prometheus format)
                 ▼           ▼
   ┌───────────────────┐   ┌─────────────────────────┐
   │    PostgreSQL     ├───►│     Grafana (:3001)     │ (Auto-provisioning дашбордов)
   │ (Хранилище в томе)│   │                         │
   └───────────────────┘   └─────────────────────────┘
```

### Принципы изоляции и сетевой безопасности:
* **Nginx reverse proxy:** Проксирует входящие запросы к сервису, передаёт заголовки `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`. В приложении активировано доверие прокси (`app.set('trust proxy', 1)`), поэтому ограничение частоты и логирование работают по реальному IP клиента.
* **Безопасность контейнеризации:** Сборка образа приложения разделена на этапы (multi-stage build). В итоговый образ не попадают dev-зависимости, а процесс выполняется не под `root`, а под пользователем `node`.
* **Сохранение состояния:** Данные PostgreSQL и настройки Grafana сохраняются в именованных томах (`pgdata`, `grafanadata`), поэтому перезапуск стека не приводит к потере данных.

## 2. Схема базы данных (3-я нормальная форма)

Реляционная схема приведена к третьей нормальной форме (3НФ), дублирование справочных данных исключено, целостность обеспечивается внешними ключами и ограничениями `UNIQUE`/`NOT NULL`.

```text
  ┌───────────────┐          1:N          ┌─────────────────────┐
  │     sites     ├──────────────────────►│      equipment      │
  └───────────────┘                       └──────────┬──────────┘
                                                     │ 1:1
                                                     ▼
                                          ┌─────────────────────┐
                                          │ equipment_passports │
                                          └─────────────────────┘
                                                     │ 1:N
                                                     ▼
  ┌───────────────┐          N:M          ┌─────────────────────┐
  │  technicians  │◄─────────────────────►│maintenance_requests│
  └───────▲───────┘ (request_assignees)   └──────────┬──────────┘
          │                                          │ 1:N
          │ 1:1 (optional)                           ▼
  ┌───────┴───────┐                       ┌─────────────────────┐
  │     users     │                       │request_status_history│
  └───────────────┘                       └─────────────────────┘
```

* **`sites` → `equipment` (1:N):** Площадка объединяет единицы оборудования. Внешний ключ `site_id` в таблице оборудования (`ON DELETE SET NULL`).
* **`equipment` → `equipment_passports` (1:1):** Технический паспорт оборудования с уникальным внешним ключом `equipment_id` (`ON DELETE CASCADE`).
* **`equipment` → `maintenance_requests` (1:N):** Заявки на обслуживание оборудования. Внешний ключ `equipment_id` защищён правилом `RESTRICT`: удаление оборудования с незакрытыми заявками запрещено.
* **`maintenance_requests` → `request_status_history` (1:N):** Иммутабельный журнал аудита статусов. Записи создаются только в рамках транзакции смены статуса и не подлежат редактированию или удалению.
* **`maintenance_requests` ↔ `technicians` (N:M):** Связующая таблица `request_assignees` с составным первичным ключом `(request_id, technician_id)` и полями `role` (`lead` | `member`) и `hours`. Повторное назначение того же специалиста на ту же заявку невозможно на уровне ограничений БД.
* **`technicians` ↔ `users` (1:1):** Учётная запись пользователя системы связывается со специалистом через `technician_id` для проверки прав выполнения работ по заявкам.

## 3. Аутентификация и разграничение прав (RBAC)

Аутентификация реализована по схеме JWT. Пароли пользователей хранятся исключительно в виде хеша с солью (`bcryptjs`, 10 раундов) и никогда не попадают ни в ответы API, ни в логи.

### Таблица ролевого доступа (RBAC):

| Маршрут / Операция | Метод | `viewer` | `technician` | `admin` |
| :--- | :--- | :---: | :---: | :---: |
| Просмотр оборудования, площадок, специалистов | `GET` | ✅ | ✅ | ✅ |
| Просмотр списка заявок и истории статусов | `GET` | ✅ | ✅ | ✅ |
| Просмотр аналитических отчётов и сводок | `GET` | ✅ | ✅ | ✅ |
| Создание заявки на обслуживание | `POST /api/requests` | ❌ (403) | ✅ | ✅ |
| Редактирование заявки | `PATCH /api/requests/:id` | ❌ (403) | ✅ | ✅ |
| Смена статуса заявки | `PATCH /api/requests/:id/status` | ❌ (403) | ⚠️ Только назначенные | ✅ Любые |
| Управление оборудованием (создание, правка, удаление) | `POST/PATCH/DELETE /api/equipment` | ❌ (403) | ❌ (403) | ✅ |
| Назначение бригады исполнителей | `POST /api/requests/:id/assignees` | ❌ (403) | ❌ (403) | ✅ |
| Удаление заявок | `DELETE /api/requests/:id` | ❌ (403) | ❌ (403) | ✅ |

### Предустановленные учетные записи (сиды):
* **Администратор:** логин `admin` / пароль `Password123!` (email: `admin@windpark.local`)
* **Техник:** логин `technician` / пароль `Password123!` (email: `tech@windpark.local`)
* **Наблюдатель:** логин `viewer` / пароль `Password123!` (email: `viewer@windpark.local`)

### Политика работы токенов и безопасность сессий:
* **Access Token:** Передаётся в заголовке `Authorization: Bearer <token>`, подписывается секретом `JWT_SECRET` и действует 15 минут.
* **Refresh Token:** Передаётся в cookie по пути `/api/auth` со следующими флагами:
  * `HttpOnly: true` — защита от чтения токена клиентскими скриптами (защита от XSS).
  * `Secure: true` — передача cookie только по защищённому протоколу (в продакшн-режиме).
  * `SameSite: strict` — запрет передачи cookie при любых кросс-доменных переходах, что полностью исключает атаки класса CSRF.
* **Защита входа:** Эндпоинт `/api/auth/login` защищён отдельным лимитом частоты запросов (rate limit). Ответ на неуспешный вход одинаков при несуществующем пользователе и неверном пароле (`401 Unauthorized`, «Неверный логин или пароль»).

## 4. Развёртывание и запуск

### 4.1. Развёртывание всего стека с нуля (Production)
Все сервисы поднимаются без правок кода, достаточно создать файл окружения и запустить Compose:
```bash
cp .env.example .env      # при необходимости поменяйте секреты JWT
docker compose up -d --build
```
Порядок запуска: PostgreSQL (healthcheck) -> одноразовый сервис `migrate` (миграции и сиды, повторный запуск безопасен) -> API (healthcheck) -> Nginx, Prometheus -> Grafana с автоматически подключёнными источниками данных, дашбордом и правилами оповещения.

Учётные записи после сидов: `admin`, `technician`, `viewer` (пароль `Password123!`).

### 4.2. Локальный запуск для разработки
1. Установка зависимостей:
   ```bash
   npm install
   ```
2. Подготовка переменных окружения:
   ```bash
   cp .env.example .env
   ```
3. Запуск контейнера PostgreSQL:
   ```bash
   docker compose up -d db
   ```
4. Применение миграций и сидов демо-данными:
   ```bash
   npm run db:migrate
   npm run db:seed
   ```
5. Запуск приложения:
   ```bash
   npm run dev
   ```

## 6. Мониторинг и метрики (Grafana & Prometheus)

* **Интерфейс Grafana:** `http://localhost:3001` (только с хоста)
* **Учётные данные:** `GRAFANA_USER` / `GRAFANA_PASSWORD` из `.env` (по умолчанию `admin` / `admin`)
* **Источники данных:** Prometheus (метрики `/metrics`, опрос каждые 10 с) и PostgreSQL (прикладные панели).
* **Provisioning:** источники данных, дашборд и правила оповещения подключаются автоматически из `deploy/grafana/` без ручной настройки в UI.
* **Метрики** закрыты в Nginx (`deny all`); проверить вручную: `docker compose exec api wget -qO- http://127.0.0.1:3000/metrics`.

### Оповещения:
* **Высокая доля ответов 5xx** (выше 5% за 5 минут, держится 2 минуты).
* **Сервис недоступен** (`up{job="maintenance-api"} < 1` в течение 1 минуты).

Порядок действий при срабатывании описан в разделе 8.2.

### Панели дашборда:
* **Технические панели:** Интенсивность входящих запросов к API, процент ответов 4xx/5xx, распределение длительности обработки (латентность) и статус доступности сервиса.
* **Прикладные панели:** Количество оборудования на учёте, число открытых заявок в работе, распределение заявок по статусам и приоритетам, среднее время закрытия заявок (MTTC в часах), количество просроченных плановых работ и сводный отчёт по нагрузке на единицы оборудования.

## 8. Эксплуатационный регламент (Runbook)

### 8.1. Проверки работоспособности (Healthchecks):
* **Liveness:** `GET /api/health/live` — проверка доступности самого процесса Node.js (возвращает статус процесса и uptime).
* **Readiness:** `GET /api/health/ready` — проверка готовности сервиса обрабатывать трафик (проверяет активное подключение к PostgreSQL через `sequelize.authenticate()`). При недоступной БД возвращает `503 Service Unavailable`, не допуская скрытого падения процесса.

### 8.2. Порядок действий при типовых сбоях:
* **Недоступность базы данных:**
  Приложение фиксирует ошибку в структурированный логгер Pino и начинает отвечать `503` на пробу `/api/health/ready`. Процесс не завершается аварийно, ожидая восстановления пула соединений. После поднятия базы пул соединений переподключается автоматически.
* **Рост доли ответов 5xx:**
  Каждый ошибочный запрос сопровождается уникальным идентификатором `requestId` в JSON-ответе клиента и в структурированных логах контейнера. Для поиска ошибки используйте:
  ```bash
  docker compose logs api | grep "REQUEST_ID_ИЗ_ОТВЕТА"
  ```
* **Сработало оповещение «Высокая доля 5xx» или «Сервис недоступен»:**
  1. `docker compose ps` и `curl -i http://localhost/api/health/ready` (жив ли процесс и доступна ли БД).
  2. `docker compose logs --tail=100 api` и поиск записей уровня `error`.
  3. По `requestId` из ответа клиента найти полную цепочку записей. При недоступной БД: `docker compose start db`, приложение переподключится само.
* **Переполнение диска:**
  `df -h`, `docker system df`, очистка неиспользуемых образов `docker image prune`. Тома `pgdata` и `grafanadata` не удалять.
* **Откат миграций базы данных:**
  Для последовательного отката всех миграций схемы выполните:
  ```bash
  npm run db:migrate:undo
  ```
  Для повторного наката:
  ```bash
  npm run db:migrate && npm run db:seed
  ```

## 9. Архитектурные решения и известные ограничения

### Принятые решения:
1. **Слоистая архитектура:** Строгое разделение ответственности по слоям (Маршруты → Контроллеры → Сервисы → Репозитории). Бизнес-логика изолирована от протокола HTTP, а доступ к данным закрыт за методами моделей Sequelize.
2. **Транзакционность и блокировки:** Смена статуса заявки с добавлением записи в журнал истории аудита выполняется в единой транзакции с пессимистической блокировкой строки (`lock: t.LOCK.UPDATE`), что предотвращает состояние гонки при конкурентных запросах.
3. **Защита от SQL-инъекций:** Все прямые SQL-запросы в аналитическом отчёте параметризованы через `replacements`. Поля сортировки строго валидируются по белому списку разрешённых колонок, исключая подстановку пользовательского ввода в `ORDER BY`.

### Известные ограничения:
* Хранилище сессий refresh-токенов построено на основе валидации подписи JWT; для мгновенного отзыва скомпрометированных токенов до истечения их срока жизни рекомендуется внедрение Redis Blacklist.

## 10. Автоматическое тестирование

Проект покрыт модульными тестами бизнес-логики и интеграционными тестами API на фреймворке Jest со связкой Supertest.

Запуск тестов (БД не нужна, слой данных подменён заглушками):
```bash
npm test                 # все тесты
npm run test:coverage    # с отчётом о покрытии (папка coverage/)
```

### Состав тестов:
* **Модульные тесты (`tests/business-logic.test.js`):** Проверка допустимых и запрещённых переходов жизненного цикла заявок (`STATUS_FLOW`), правила обязательного наличия ровно одного ведущего специалиста (`lead`) в бригаде, логика разграничения прав по ролям.
* **Интеграционные тесты (`tests/integration.test.js`):** Проверка отдачи liveness-пробы, выгрузки метрик `/metrics`, пресечение неавторизованного доступа (`401 Unauthorized`), валидация нейтрального ответа при ошибке аутентификации.
